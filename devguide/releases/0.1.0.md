## Included scope

The [implementation guide](../FIRST_SLICE.md) and [changelog](../../CHANGELOG.md)
define the implemented API. Cataloging, scoped methodological review, selection,
execution, quantities/contracts, bounded composition, operational recording,
attribution, auditing, reporting and descriptive benchmarks are included.
API and storage formats may evolve in subsequent 0.x versions.

Hydrogen definitions are pending proposals with no executable provider binding or
scientific admission. Their provider work stays in [MolSysMT #323](https://github.com/uibcdf/molsysmt/issues/323).
The shared invocation/Run/ExecutionPlan and partial-commit contract stays in
[MOLI #28](https://github.com/uibcdf/moli/issues/28). Neither needs to be completed
to release the explicitly scoped local runner. Execution is sequential; no
parallel/distributed backend, durable suspension/resume or rollback is promised.

## Qualification procedure

These are the original gates fulfilled for the frozen source above. Future
candidates need evidence for their own exact source, artifacts and dependency closure.

1. Integrate the local implementation with current main and record a reviewable commit.
2. Run Ruff, local/canonical governance and dependency preflight on the exact candidate.
   Required dependencies and present optional providers must meet declared bounds.
3. Build one immutable noarch Conda candidate through the reviewed shared UIBCDF
   action (`v2.3.0`, source `87c70b1443d5f22d738ee3ddf812bdbe0152f6c2`) with `upload=false`.
   Keep wheel and source archives for private qualification, with no PyPI route claim.
4. Inspect each archive's complete Python/JSON runtime resource inventory and version.
   Negative regressions reject missing resources and stale version identities per route.
5. Install the same Conda artifact on Linux and macOS arm64 for Python 3.11–3.14,
   with published required and optional providers. Check artifact hash, actual import
   path, runtime resources, dependency bounds, full tests and resolved closure.
   The real MolSysMT test may skip when that optional scientific provider is absent;
   Recorda/Ackredit qualification is required and must not skip.
6. Qualify the retained wheel on Linux Python 3.14. Store hashes, exact source SHA,
   environment manifests, instrumented coverage XML and JUnit results in attempt-qualified CI artifacts.
7. Complete owner-local ecosystem, distribution and OS-support reviews under #9;
   request MOLI Python-package registration with those references. Record coverage
   producer/adoption and archival applicability; withhold unsupported badges.
8. Before tagging, record the exact candidate's gate results in #9, including any
   changed/stale evidence. A new source commit requires fresh source/combined gates.
   Follow the canonical [MOLI version policy](https://github.com/uibcdf/moli/blob/main/devguide/policies/release_version_policy.md).

The workflow named `build_and_upload_conda_packages.yaml` satisfies the conventional
recipe route location but deliberately only builds an unpublished candidate.
It takes no publication credentials. The tests workflow consumes its exact file;
manual execution of the builder alone does not certify the installed matrix.

## Publication and claims

Target public route: `uibcdf` Conda with `conda-forge`. No public PyPI route is planned.
Keep the tested artifact and its digest; never replace an occupied registry coordinate,
even under another label. A later upload/promote decision must inspect all-label
coordinate occupancy, use the same qualified bytes and independently verify public
poststate before adding installation instructions or distribution badges.

The public source tag exists. No Conda upload, public PyPI route, GitHub Release
or verified Zenodo archive is claimed. The successful read-only hosted check
observed an available effective CI credential; write authorization, actual upload,
public poststate and clean public-channel installation remain unexercised.
Scientific admission remains a separate human/domain decision.

Qualified component support is Linux x86_64 and macOS arm64, Python 3.11–3.14.
Windows and Intel macOS are unclaimed. The matching MOLI registry proposal remains
pending merge; a pending registry mirror does not turn component acceptance into
an untested support target.
